# 知识库检索服务详细设计文档（v2.0）

---

## 1. 引言

### 1.1 背景与目标
本服务是智能问答系统的核心检索组件，负责接收用户自然语言问题，通过“问题分类 + Schema 化查询扩展 + 加权字段匹配”策略，从预构建的文档 Chunk 库中检索出最相关的文本块，供后续生成模块使用。  
本阶段仅实现检索接口，不包含答案生成与对话管理。

### 1.2 设计约束与选型
- **语言**：Python 3.10+
- **部署**：本地服务器，无需外部云服务
- **大模型**：OpenAI 兼容接口（本地私有化部署的 LLM）
- **检索引擎**：Whoosh（纯 Python 全文索引库，零额外依赖）
- **数据来源**：已解析为固定格式 JSON，通过 Pydantic 模型 `Document` 加载，每个文档一个 JSON 文件，内含分块、实体、关系及目录树。
- **接口形态**：仅提供检索 API，返回排序后的相关 Chunk 列表及得分。

### 1.3 文档结构
- 第 2 章：系统总体架构与模块划分
- 第 3 章：数据模型与存储设计
- 第 4 章：问题分类与 Schema 定义（可配置化）
- 第 5 章：查询扩展模块（结构化提取器）
- 第 6 章：Whoosh 索引构建与字段设计
- 第 7 章：匹配计分与查询执行
- 第 8 章：API 接口设计
- 第 9 章：配置与启动
- 附录：配置示例、模型清单、依赖等

## 2. 系统总体架构

### 2.1 模块分层

```
┌──────────────────────────────────────┐
│          API 层（FastAPI）            │
│  POST /retrieve → List[ChunkScore]   │
└──────────────┬───────────────────────┘
               │
┌──────────────▼───────────────────────┐
│       查询处理管道 (Pipeline)         │
│  ┌─────────────────────────────┐     │
│  │ 问题分类器 (Classifier)     │     │
│  └──────────┬──────────────────┘     │
│             ▼                        │
│  ┌─────────────────────────────┐     │
│  │ 结构化提取器 (Extractor)    │     │
│  │  (LLM + Schema Prompt)     │     │
│  └──────────┬──────────────────┘     │
│             ▼                        │
│  ┌─────────────────────────────┐     │
│  │  查询构造器 (Query Builder) │     │
│  └──────────┬──────────────────┘     │
│             ▼                        │
│  ┌─────────────────────────────┐     │
│  │  检索引擎适配器 (Whoosh)    │     │
│  └─────────────────────────────┘     │
└──────────────────────────────────────┘
               │
┌──────────────▼───────────────────────┐
│        数据层 (Data Layer)            │
│  ┌─────────────────────────────┐     │
│  │ 文档加载器 (JSON→Document)  │     │
│  └──────────┬──────────────────┘     │
│             ▼                        │
│  ┌─────────────────────────────┐     │
│  │ 索引构建器 (Whoosh Index)   │     │
│  └─────────────────────────────┘     │
└──────────────────────────────────────┘
```

### 2.2 核心模块职责
- **API 层**：接收 HTTP 请求，参数校验，调用管道，返回结果。
- **问题分类器**：基于规则或小模型判断问题类别（预定义 5~8 类），返回类别 ID。
- **结构化提取器**：调用本地 LLM，按类别对应的 JSON Schema 从问题中提取字段值。
- **查询构造器**：将提取的字段映射为 Whoosh 查询 DSL，保留字段权重。
- **检索引擎适配器**：对 Whoosh 的封装，接收查询 DSL，执行多字段组合搜索，返回带得分的 Chunk ID 列表。
- **数据层**：
  - **文档加载器**：扫描指定目录下的 JSON 文件，反序列化为 `Document` 对象，并提取所有 `Chunk` 的元数据。
  - **索引构建器**：在服务启动或离线阶段，将 Chunk 数据批量写入 Whoosh 索引，定义各字段的索引方式与权重（此处权重为索引层 boost，但计分仍在检索时动态调整）。

### 2.3 数据流向
1. 用户问题 → API `/retrieve`。
2. 问题分类器 → 类别 `c`。
3. 获取类别 `c` 对应的 Schema `S`（从配置文件加载）。
4. 提取器以 `(问题, S)` 为 Prompt 调用 LLM，得到结构化字段 `Q`。
5. 查询构造器将 `Q` 中的字段转化为 Whoosh `query` 对象：
   - `entity_name` → 实体名索引字段（精确/模糊）
   - `relation_pred` → 关系谓词字段
   - `time` / 标题关键词 → 标题字段
   - `metric` / 自由文本 → 内容字段
   - 各字段按 Schema 权重设置 boost。
6. 检索适配器执行 `searcher.search(query, limit=K)`，返回 `(chunk_id, score)`。
7. 按得分降序排列，截取前 K 个，根据 `chunk_id` 回源获取 `Chunk` 完整信息（可选择性包含前后相邻块用于上下文），封装返回。

## 3. 数据模型与存储设计

### 3.1 数据源格式
所有文档已预解析为 JSON 文件，每个文件对应一个 `Document` 实例，存放在配置指定的目录下。JSON 结构与 Pydantic 模型一致，包含 `doc_id`、`doc_type`、`version_ts`、`chunks` 列表与 `doc_tree`。

### 3.2 运行时存储设计
检索服务对延迟敏感，且语料规模不大（通常 100~1000 份文档，总 Chunk 数 10⁴~10⁵ 级），采用 **全内存加载 + Whoosh 倒排索引** 双层存储。

#### 3.2.1 内存映射结构
- **chunk_dict**：`dict[str, Chunk]`，键为 `chunk_id`，值为完整的 `Chunk` Pydantic 对象。用于检索后回源组装结果，并提供相邻块扩展。
- **doc_dict**：`dict[str, Document]`，键为 `doc_id`，值为完整的 `Document` 对象。保留目录树 `doc_tree` 等元信息，供后续功能扩展（如章节范围过滤）。
- **chunk_to_doc**：`dict[str, str]`，记录每个 `chunk_id` 所属的 `doc_id`，便于快速定位。

内存占用估算：假设 10 万 Chunk，每条 Chunk 平均 2KB，总内存约 200MB，完全可接受。

#### 3.2.2 Whoosh 索引结构
Whoosh 索引用于执行全文搜索和字段级加权匹配，**只存储必要字段用于检索与回源定位，不存储完整实体/关系列表**。索引字段设计如下：

| 字段名 | 类型 | 存储 | 说明 |
|--------|------|------|------|
| `chunk_id` | `ID(stored=True, unique=True)` | 是 | 主键，用于回内存取完整 Chunk |
| `doc_id` | `ID(stored=True)` | 是 | 所属文档 ID |
| `section_title` | `TEXT(stored=True, analyzer=default_analyzer)` | 是 | 章节标题，用于标题通道匹配 |
| `section_path` | `TEXT(stored=True)` | 是 | 章节路径，可辅助过滤 |
| `content` | `TEXT(stored=True, analyzer=default_analyzer)` | 是 | 正文内容，用于内容通道兜底匹配 |
| `entity_names` | `TEXT(stored=True, analyzer=default_analyzer)` | 是 | 所有实体名称拼接（空格分隔），用于实体名精确/模糊匹配 |
| `entity_descs` | `TEXT(stored=True, analyzer=default_analyzer)` | 是 | 所有实体描述拼接，用于实体描述匹配 |
| `relation_predicates` | `TEXT(stored=True)` | 是 | 所有关系谓词拼接，用于关系谓词匹配 |
| `relation_objects` | `TEXT(stored=True)` | 是 | 所有关系客体拼接，用于客体匹配 |
| `chunk_index` | `NUMERIC(stored=True)` | 是 | 块序号，排序或调试用 |
| `prev_chunk_id` | `ID(stored=True)` | 是 | 前一个块 ID，用于上下文扩展 |
| `next_chunk_id` | `ID(stored=True)` | 是 | 后一个块 ID，用于上下文扩展 |

> **为什么不直接存实体/关系对象？**  
> 索引存储冗余数据会增加索引体积，且复杂结构需序列化为文本。采用外存（内存字典）回源方式，检索后通过 `chunk_id` 直接获取 Pydantic 对象，代码更简洁，性能也足够。

**自定义分析器**：使用 Whoosh 默认的 `StandardAnalyzer`，配合小写化、停用词过滤和中文分词（需安装 `jieba`，并集成 `ChineseAnalyzer`）。实际部署时推荐基于 `jieba` 的自定义分析器，以保证中文语义匹配质量。

### 3.3 索引构建流程
1. **文档加载**：遍历数据目录下的 `.json` 文件，使用 `Document.parse_file()` 反序列化。
2. **填充内存映射**：遍历每个 `Document` 的 `chunks` 列表，将 `Chunk` 对象存入 `chunk_dict`，记录 `chunk_to_doc` 映射，并将整个 `Document` 存入 `doc_dict`。
3. **写入索引**：对每个 `Chunk`，构建索引文档：
   - `entity_names` 字段：提取 `[e.name for e in chunk.entities]`，用空格连接。
   - `entity_descs` 字段：提取 `[e.desc for e in chunk.entities]`，用空格连接。
   - `relation_predicates`：`[r.predicate for r in chunk.relations]`，空格连接。
   - `relation_objects`：`[r.object for r in chunk.relations]`，空格连接。
   - 其余字段直接赋值。
4. **索引存储目录**：索引文件默认保存在 `index/` 目录，可通过配置变更。

**增量更新**（可选）：若文档版本更新（`version_ts` 变化），可通过对比时间戳重新索引对应文档。简单实现可每次启动时全量重建，定期重启即可。

### 3.4 回源与上下文扩展
检索接口返回 `List[RetrievedChunk]`，每个 `RetrievedChunk` 除包含原始 `Chunk` 的全部字段外，还可选择性附带**前后相邻块**的内容，以增强下游生成模块的上下文连贯性。

实现方法：
- 从 Whoosh 获得 Top-K 的 `chunk_id` 列表。
- 对每个 `chunk_id`，从 `chunk_dict` 取出 `Chunk`。
- 根据 `prev_chunk_id` 和 `next_chunk_id`，再从字典取出相邻块（可控制扩展深度，默认各取 1 个）。
- 组装成 `RetrievedChunk` 对象返回。

`RetrievedChunk` Pydantic 模型建议定义：
```python
class RetrievedChunk(BaseModel):
    chunk: Chunk
    score: float
    prev_chunks: List[Chunk] = []
    next_chunks: List[Chunk] = []
```

### 3.5 数据一致性保障
- 所有数据为只读，无并发写入问题。
- 索引构建在服务启动阶段同步完成，之后服务才监听端口，保证启动后的内存与索引完全对应。
- 如需热更新文档，可提供管理接口触发索引增量刷新，并加读写锁控制。当前版本暂不实现。

## 4. 问题分类与 Schema 定义（可配置化设计）

### 4.1 设计原则
为了避免每次调整问题类别或提取字段时重新修改代码、重新部署服务，本模块的设计完全由外部配置文件驱动。  
**核心原则**：
- **零代码变更**：新增、删除、修改问题类别，只需修改配置文件，服务热加载或重启即可生效。
- **分类策略可配**：每个类别可指定使用关键词规则或直接调用 LLM 进行分类，并可在配置中定义关键词权重、匹配阈值等参数。
- **Schema 完全外置**：每个类别的结构化提取 Schema（字段名、类型、权重、目标索引字段等）以 JSON 文件独立存储，服务启动时动态加载校验。
- **兜底机制**：配置文件中必须定义一个“默认类别”，用于无法匹配任何规则的情况。

### 4.2 配置文件体系
配置文件统一存放在 `config/` 目录下，目录结构如下：

```
config/
├── categories.yaml          # 类别定义与分类规则
└── schemas/
    ├── business_dev.json    # 示例：业务板块发展类 Schema
    ├── finance.json
    ├── risk.json
    ├── strategy.json
    ├── esg.json
    ├── tech.json
    └── default.json         # 兜底类别 Schema
```

#### 4.2.1 类别配置文件：`categories.yaml`
该文件描述所有支持的类别及其分类规则，每个类别包含：唯一标识、中文名称、分类方法（规则或 LLM）、规则参数以及关联的 Schema 文件路径。

```yaml

  - id: "strategy"
    name: "战略与举措"

  - id: "esg"
    name: "ESG与荣誉"
    schema_file: "schemas/esg.json"

        - words: ["ESG", "评级", "奖项", "荣誉", "绿色", "环保", "社会责任", "sustainability"]
          weight: 1.0

  - id: "tech"
    name: "研发与技术"
```

**配置说明**：
- `id` 为程序内部使用的类别唯一标识。
- `schema_file` 指向具体 Schema 文件，路径相对于 `config/`。
- `classification.method` 可选 `keyword` / `llm` / `default`。
- `keyword` 方法下，可定义多组关键词 `words` 及其权重；系统对问题文本分词后，计算命中关键词的加权得分，超过 `threshold` 即匹配。
- 如果多个类别得分均超过阈值，取最高分；若均未超过阈值，回退到 `default` 类别。

#### 4.2.2 Schema 配置文件
每个类别对应一个 JSON 文件，定义需要提取的字段、目标索引字段、匹配方式和权重。以 `business_dev.json` 为例：

```json

      "required": false

    {
      "field_name": "relation_predicate",
```

### 4.3 分类器实现逻辑（纯配置驱动）
分类器由 `Classifier` 类实现，其工作流程如下：
1. **加载配置**：启动时读取 `config/categories.yaml`，反序列化为 `List[CategoryConfig]`（Pydantic 模型）。同时加载所有 Schema 文件到 `schema_registry: dict[str, CategorySchema]`。
2. **分类决策**：接收问题文本 `question`。
   - 遍历所有非 `default` 类别，根据其 `classification.method` 计算得分：
     - **keyword**：使用 jieba 对问题分词，统计每个关键词组的命中词数，计算加权得分：`score = Σ(group_weight * (命中词数 / 总词数))`（可归一化），若得分 ≥ threshold 则将该类别加入候选。
     - **llm**：调用 LLM 分类（预留逻辑，暂不默认启用）。
   - 选择候选类别中得分最高的；若无候选，则选用 `default` 类别。
3. **返回**：得到最终类别 ID 和对应的 `CategorySchema`。

**可扩展性保障**：
- 若业务人员要新增一个类别，只需：
  1. 在 `categories.yaml` 中增加一个条目，设定 ID、名称、关键词和阈值。
  2. 在 `schemas/` 下增加对应的 JSON 文件，定义提取字段。
  3. 重启服务（或热加载配置），无需修改任何代码。
- 修改现有类别的关键词、Schema 字段权重等同理。

### 4.4 分类与 Schema 的运行时数据结构
在代码中流转方便，定义以下 Pydantic 模型：

```python
class CategoryConfigKeywordGroup(BaseModel):
    words: List[str]
    weight: float

class CategoryConfigClassification(BaseModel):
    method: Literal["keyword", "llm", "default"]
    keywords: Optional[List[CategoryConfigKeywordGroup]] = None
    threshold: Optional[float] = None

class CategoryConfig(BaseModel):
    id: str
    name: str
    description: str = ""
    schema_file: str
    classification: CategoryConfigClassification

class SchemaField(BaseModel):
    field_name: str
    field_type: str
    description: str
    target_index_field: str
    match_method: Literal["exact_then_fuzzy", "fuzzy", "substring"]
    weight: float
    required: bool = False

class ChannelWeights(BaseModel):
    entity_channel: float = 0.4
    relation_channel: float = 0.3
    title_channel: float = 0.2
    content_channel: float = 0.1

class CategorySchema(BaseModel):
    category_id: str
    category_name: str
    description: str = ""
    fields: List[SchemaField]
    default_channel_weights: ChannelWeights
```

服务启动时，`ConfigManager` 负责解析 YAML/JSON 并完成模型校验，将 `categories` 列表和 `schema_registry` 字典注入给分类器和提取器使用。

### 4.5 热加载与运维支持（可选拓展）
为方便调试，可提供以下辅助能力（当前版本不强制实现，但在设计上预留接口）：
- 通过 API `/admin/reload-config` 触发配置重载（需加锁保证线程安全）。
- 将 `categories.yaml` 和 `schemas/` 目录放在外部挂载卷中，方便运维直接修改。
- 对每个请求，可在返回结果中携带 `category_used` 字段，便于监控分类准确率和调整关键词。

## 5. 查询扩展模块（结构化提取器）

### 5.1 模块职责
查询扩展模块负责将原始自然语言问题，结合问题分类器确定的类别及其 Schema，转换为一个**结构化的查询描述对象**（`StructuredQuery`）。该对象包含了按 Schema 字段提取的具体值、对应索引字段和权重，供后续查询构造器使用。

核心输入输出：
- **输入**：问题文本 `question`、类别对应的 `CategorySchema`。
- **输出**：`StructuredQuery` 实例，内含多个 `QueryField`（每个对应一个 Schema 字段的提取值，若无法提取则为 None）。

### 5.2 结构化查询数据模型
```python
class QueryField(BaseModel):
    """单个查询字段的提取值与匹配元信息"""
    field_name: str
    value: Optional[str] = None
    target_index_field: str
    match_method: str
    weight: float

class StructuredQuery(BaseModel):
    """结构化查询对象，由提取器生成"""
    category_id: str
    fields: List[QueryField]
    free_text: Optional[str] = None
    channel_weights: ChannelWeights
```

### 5.3 提取方式：基于 LLM 的 Schema 填空
调用本地 LLM（OpenAI 兼容接口）完成任务。Prompt 设计遵循以下原则：
- 严格按给定 Schema 输出 JSON，不额外解释。
- 字段无法提取时填 `null`，不编造信息。
- 对时间、数字等保持原文字段值，不做归一化。
- 通过 `required` 标记强调重要性，但允许 LLM 判断。

#### 5.3.1 Prompt 模板
```
你是一个信息提取专家。根据问题类别和提取字段要求，从问题中抽取对应的结构化信息。
- 严格输出 JSON，不要包含任何其他文字或 markdown 标记。
- 如果某个字段无法从问题中提取，该字段值设为 null。
- 不要编造信息。

问题类别：{category_name}
提取字段说明：
{fields_description}

问题：{question}

输出示例：
{example_json}
```

其中：
- `{fields_description}` 由 Schema 的每个字段生成，形如：
  ```
  - entity_name (必填): 公司名称或业务板块名称，如“美的”、“暖通楼宇”。
  - time (选填): 年份或时间指示词，如“2025年”。
  - relation_predicate (选填): 关系谓词，如“发展重点”、“战略”。
  ```
- `{example_json}` 根据字段动态生成，如：
  ```json
  {"entity_name": "美的", "time": "2025年", "relation_predicate": "发展重点"}
  ```

#### 5.3.2 LLM 调用封装
实现 `LLMExtractor` 类：
```python
class LLMExtractor:

        self.client = openai.OpenAI(base_url=api_base, api_key=api_key)
        self.model = model
        self.temperature = temperature

    def extract(self, question: str, schema: CategorySchema) -> Dict[str, Optional[str]]:
```

**异常处理**：
- 网络错误/超时：重试 1 次，仍失败则抛出 `ExtractionError`，上层可降级为仅使用 `free_text` 进行全文检索。
- JSON 解析失败：尝试正则提取 JSON 字符串，再失败则同样降级。
- 字段类型校验：不做严格类型转换，所有值均保留字符串形式。

#### 5.3.3 模型选型建议
建议使用 **Qwen2.5-7B-Instruct** 或类似级别的轻量模型，延迟控制在 200~500ms 内。

### 5.4 降级策略与容错设计
为保证服务鲁棒性，设计多级降级：
1. **LLM 调用成功** → 正常得到 `fields_dict`。
2. **LLM 不可用或超时** → 放弃提取，构造仅含 `free_text` 的 `StructuredQuery`，使用默认类别通道权重进行纯内容检索。
3. **LLM 返回不完整，但至少有一个非 null 字段** → 使用该部分字段构造查询，缺失字段权重按比例重新分配给其余字段。

降级逻辑由 `ExtractorOrchestrator` 封装，它对 `LLMExtractor` 的调用进行包装。

### 5.5 从提取结果构建 StructuredQuery
流程：
1. 将 `LLMExtractor.extract()` 返回的 `dict` 与 `CategorySchema.fields` 对齐。
2. 对每个 `SchemaField`，查找对应键的值，生成 `QueryField` 对象。
3. 过滤掉 `value is None` 的 `QueryField`（除非后续采用了“权重重分配”策略，此时暂保留但值为空）。
4. 若所有字段值均为 None，启用降级：将整个问题文本作为 `free_text`，目标字段改为 `content`，权重置为 1.0，通道权重全给内容通道。
5. 构造 `StructuredQuery` 对象，同时携带 `category_id` 和 `channel_weights`。

```python
class QueryBuilder:
    @staticmethod
    def build(schema: CategorySchema, extracted: Dict[str, Optional[str]]) -> StructuredQuery:
        fields = []
        for sf in schema.fields:
            val = extracted.get(sf.field_name)
            fields.append(QueryField(
                field_name=sf.field_name,
                value=val,
                target_index_field=sf.target_index_field,
                match_method=sf.match_method,
                weight=sf.weight
            ))
        has_value = any(qf.value is not None for qf in fields)
        if not has_value:
            fields = [QueryField(
                field_name="query_text",
                value="PLACEHOLDER",  # 由调用方填入原始问题
                target_index_field="content",
                match_method="fuzzy",
                weight=1.0
            )]
            channel_weights = ChannelWeights(
                entity_channel=0.0, relation_channel=0.0, title_channel=0.0, content_channel=1.0
            )
        else:
            channel_weights = schema.default_channel_weights
        return StructuredQuery(
            category_id=schema.category_id,
            fields=fields,
            free_text="PLACEHOLDER",
            channel_weights=channel_weights
        )
```
（注：`free_text` 的实际赋值在管道代码中直接使用原始问题字符串。）

### 5.6 与管道其他模块的交互
在检索管道中，执行顺序为：
1. 分类器给出 `CategorySchema`。
2. 提取器调用 LLM，得到 `extracted_dict`。
3. `QueryBuilder` 生成 `StructuredQuery`。
4. `WhooshSearcher` 接收 `StructuredQuery` 执行搜索。

管道伪代码：
```python
def retrieve_pipeline(question: str, options: dict):
    category_config, schema = classifier.classify(question)
    try:
        extracted_dict = llm_extractor.extract(question, schema)
    except ExtractionError:
        schema = schema_registry["default"]
        extracted_dict = {"query_text": question}
    structured_q = query_builder.build(schema, extracted_dict)
    structured_q.free_text = question
    results = whoosh_searcher.search(structured_q, top_k=options.get("top_k", 10))
    return assemble_response(results)
```

## 6. Whoosh 索引构建与字段设计

### 6.1 总体方案
Whoosh 是本服务的核心检索引擎，负责存储所有 Chunk 的可搜索元数据并提供多字段加权检索能力。索引在服务启动时自动构建，采用基于 `jieba` 的中文分析器以保证分词质量，所有 Chunk 数据从 `Document` JSON 文件读取并批量写入，构建完成后索引文件持久化到磁盘，后续重启时可直接复用，仅当配置要求“强制重建”或数据文件有更新时（通过 `version_ts` 检测）才触发重新索引。

### 6.2 索引字段详细设计
每个 Chunk 对应一个 Whoosh 文档（`Document`），包含以下字段（同 3.2.2 节，略）。

### 6.3 分析器配置
自定义中文分析器 `chinese_analyzer` 的构建：
```python
import whoosh.analysis as analysis
from whoosh.analysis import Tokenizer, Token
import jieba

class JiebaTokenizer(Tokenizer):
    def __call__(self, value, positions=False, chars=False,
                 keeporiginal=False, removestops=True,
                 start_pos=0, start_char=0, mode='', **kwargs):
        tokens = jieba.lcut(value)
        for pos, token in enumerate(tokens):
            t = Token(positions=pos, text=token.lower(), boost=1.0)
            yield t

custom_analyzer = JiebaTokenizer() | analysis.LowercaseFilter() | analysis.StopFilter()
```

若 `jieba` 不可用，可回退为 `StemmingAnalyzer`。

### 6.4 索引 Schema 定义
```python
from whoosh import fields

INDEX_SCHEMA = fields.Schema(
    chunk_id=fields.ID(stored=True, unique=True),
    doc_id=fields.ID(stored=True),
    section_title=fields.TEXT(stored=True, analyzer=custom_analyzer),
    section_path=fields.TEXT(stored=True, analyzer=custom_analyzer),
    content=fields.TEXT(stored=True, analyzer=custom_analyzer),
    entity_names=fields.TEXT(stored=True, analyzer=custom_analyzer),
    entity_descs=fields.TEXT(stored=True, analyzer=custom_analyzer),
    relation_predicates=fields.TEXT(stored=True, analyzer=custom_analyzer),
    relation_objects=fields.TEXT(stored=True, analyzer=custom_analyzer),
    chunk_index=fields.NUMERIC(stored=True, numtype=int),
    prev_chunk_id=fields.ID(stored=True),
    next_chunk_id=fields.ID(stored=True),
)
```

### 6.5 索引构建与加载流程
服务启动时，`IndexManager` 负责检查和创建索引：
1. **检查索引目录**：如果目录存在且未设置强制重建标志，直接打开现有索引。
2. **如果不存在或需要重建**：从数据文件加载所有 `Document` 并构建索引。
   - **文档加载**：遍历数据目录下所有 `.json` 文件，使用 `Document.parse_file()` 加载，同时填充内存映射 `chunk_dict`、`doc_dict`。
   - **写入索引**：
     ```python
     writer = index.writer()
     for doc in documents:
         for chunk in doc.chunks:
             writer.add_document(
                 chunk_id=chunk.chunk_id,
                 doc_id=chunk.doc_id,
                 section_title=chunk.section_title,
                 section_path=chunk.section_path,
                 content=chunk.content,
                 entity_names=" ".join(e.name for e in chunk.entities),
                 entity_descs=" ".join(e.desc for e in chunk.entities),
                 relation_predicates=" ".join(r.predicate for r in chunk.relations),
                 relation_objects=" ".join(r.object for r in chunk.relations),
                 chunk_index=chunk.chunk_index,
                 prev_chunk_id=chunk.prev_chunk_id or "",
                 next_chunk_id=chunk.next_chunk_id or "",
             )
     writer.commit(optimize=True)
     ```

### 6.6 增量更新策略（可选）
通过定期检查文档版本，利用 `delete_by_term("doc_id", doc_id)` 删除旧块再写入新块实现。当前简单实现每次重启全量重建。

### 6.7 性能考量
- 10 万 Chunk 索引构建时间约 10 秒。
- 索引文件体积约为原始文本的 30%~50%。
- 查询延迟在 10ms 级别。

## 7. 匹配计分与查询执行

### 7.1 模块职责
`WhooshSearcher` 负责将 `StructuredQuery` 转化为 Whoosh 查询对象，执行检索并返回带得分的 Chunk ID 列表。核心任务包括：
- 根据 `QueryField` 生成针对不同索引字段的查询子句。
- 按字段权重和通道权重合成最终查询。
- 处理无有效字段时的降级全文搜索。
- 支持结果数量控制、得分阈值过滤、上下文扩展等后处理。

### 7.2 单字段查询构造
对每个 `QueryField`，根据其 `match_method` 生成查询子句：
- **`exact_then_fuzzy`**：构造 `Or([Term(field, val), FuzzyTerm(field, val, maxdist=2)])`（若为短语，先分词用 `Phrase` 查询）。
- **`fuzzy`**：直接使用 `FuzzyTerm`。
- **`substring`**：提取关键词后转 `Term` 或 `FuzzyTerm`；若失败则降级为 `Wildcard(field, f"*{val}*")`。

实现中统一使用 `Or([Term, FuzzyTerm])` 并赋予不同 boost 来体现精确匹配优先。

### 7.3 通道分组与权重合成
采用**方案 A：分通道独立查询 + 应用层加权求和**。

1. 根据 `QueryField.target_index_field` 将字段分配到四个通道组：
   - Entity 通道：`entity_names`, `entity_descs`
   - Relation 通道：`relation_predicates`, `relation_objects`
   - Title 通道：`section_title`, `section_path`
   - Content 通道：`content`（及 `free_text`）
2. 对每个通道，构造 `Or` 查询，子句内部按字段权重的归一化值设置 boost。
3. 分别执行 `searcher.search(channel_query, limit=None)`，获取每个 Chunk 的原始得分。
4. 对各通道分数进行 **最大最小归一化** 映射到 [0,1] 区间。
5. 加权求和：`total = Σ(channel_weight * norm_score)`。
6. 按 `total` 降序取 Top-K。

通道权重优先使用 `StructuredQuery.channel_weights`；若某通道无有效字段，权重按比例分配至其余通道，保证权重和为 1。

### 7.4 得分归一化
```python
def _normalize_channel_scores(self, channel_scores):
    norm = {}
    for ch, scores in channel_scores.items():
        if not scores: 
            norm[ch] = {}
            continue
        vals = list(scores.values())
        vmin, vmax = min(vals), max(vals)
        if vmax == vmin:
            norm[ch] = {k: 1.0 for k in scores}
        else:
            norm[ch] = {k: (v - vmin) / (vmax - vmin) for k, v in scores.items()}
    return norm
```

### 7.5 降级全文搜索
当 `StructuredQuery` 中无有效字段值（全部为 None 或 free_text 回退），跳过通道分离，直接对 `content` 字段执行 `Or` 查询（问题分词后构造），取 top-K。

### 7.6 搜索结果后处理
1. 截取 K：默认 10，可配置。
2. 低分过滤：总分低于阈值（默认 0.01）丢弃。
3. 去重与分数累加：在合并各通道得分时使用同一个 `score_dict` 累加。
4. 上下文扩展：根据 `prev_chunk_id` / `next_chunk_id` 获取相邻块。
5. 返回 `List[RetrievedChunk]`。

### 7.7 核心代码骨架
```python
class WhooshSearcher:
    def __init__(self, index, chunk_dict):
        self.index = index
        self.chunk_dict = chunk_dict

    def search(self, structured_q: StructuredQuery, top_k: int = 10) -> List[RetrievedChunk]:
        channel_queries = {
            "entity": self._build_channel_query(structured_q, ["entity_names", "entity_descs"]),
            "relation": self._build_channel_query(structured_q, ["relation_predicates", "relation_objects"]),
            "title": self._build_channel_query(structured_q, ["section_title", "section_path"]),
            "content": self._build_channel_query(structured_q, ["content"]),
        }
        channel_scores = {}
        with self.index.searcher() as searcher:
            for ch, q in channel_queries.items():
                if q is None:
                    channel_scores[ch] = {}
                    continue
                results = searcher.search(q, limit=None)
                channel_scores[ch] = {hit["chunk_id"]: hit.score for hit in results}
        norm_scores = self._normalize_channel_scores(channel_scores)
        total_scores = defaultdict(float)
        ch_weights = structured_q.channel_weights
        for ch, scores in norm_scores.items():
            w = getattr(ch_weights, f"{ch}_channel")
            for cid, s in scores.items():
                total_scores[cid] += w * s
        sorted_ids = sorted(total_scores.keys(), key=lambda x: total_scores[x], reverse=True)[:top_k]
        results = []
        for cid in sorted_ids:
            if total_scores[cid] < MIN_SCORE_THRESHOLD:
                continue
            chunk = self.chunk_dict[cid]
            prev_chunks = []
            if chunk.prev_chunk_id and chunk.prev_chunk_id in self.chunk_dict:
                prev_chunks.append(self.chunk_dict[chunk.prev_chunk_id])
            next_chunks = []
            if chunk.next_chunk_id and chunk.next_chunk_id in self.chunk_dict:
                next_chunks.append(self.chunk_dict[chunk.next_chunk_id])
            results.append(RetrievedChunk(
                chunk=chunk,
                score=total_scores[cid],
                prev_chunks=prev_chunks,
                next_chunks=next_chunks,
            ))
        return results
```

  ```yaml
    temperature: 0.0
  ```

### 9.3 环境变量覆盖
支持前缀 `RETRIEVER_` 覆盖，如 `RETRIEVER_SERVER_PORT=9000`。优先级：环境变量 > 配置文件。

### 9.4 启动流程
1. 解析命令行参数（`--config`, `--force-rebuild`）。
2. 加载并校验配置（包括 Schema 文件）。
3. 初始化 `IndexManager`：加载数据，填充内存，打开或构建索引。
4. 初始化 `Classifier`, `LLMExtractor`, `QueryBuilder`, `WhooshSearcher`。
5. 组装检索管道。
6. 创建 FastAPI 应用，注册路由。
7. 启动 uvicorn。

示例 `main.py` 骨架见前文。

### 9.5 容器化部署建议
基础镜像 `python:3.10-slim`，依赖：`fastapi, uvicorn, pydantic, whoosh, jieba, openai, pyyaml`。  
通过卷挂载数据与配置文件。单 worker 即可满足性能。
